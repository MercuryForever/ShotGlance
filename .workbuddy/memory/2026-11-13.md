## 路径无关性查证（用户提出"最终版不硬性固定路径"）

逐层查了运行时路径解析，**结论是这条约束本来就不存在，是误解**：

- 源码零硬编码绝对路径。模型走 `SHOTGLANCE_MODELS` → exe 同级 → `../Resources` → `CARGO_MANIFEST_DIR`（4 顺位）；dll 走 `SHOTGLANCE_ORT_DLL` → exe 同级 → exe/models → ../Resources → `CARGO_MANIFEST_DIR/vendor`（5 顺位）；离线模型走 `%APPDATA%\ShotGlance\…`；配置走 `app_config_dir()`；tokens.tsv 走 `BaseDirectory::Resource`。
- **唯一残留**：两处 `env!("CARGO_MANIFEST_DIR")` dev fallback 会被烧进二进制，但正常安装布局下走不到。
- `restore-env-bundle.ps1:210-233` 路径不符时是 **Warn + 跳过 target**，工具链/crate 缓存/node_modules 照常恢复 → 路径不同只多花 30 分钟重编，功能零影响。
- 即：真正的约束是"想复用 target 缓存就得同路径"，缓存是**优化项**不是**依赖项**。
- 待办（未经用户确认）：两处 fallback 加 `#[cfg(debug_assertions)]`；release 加 `--remap-path-prefix`（未实测）；`CARGO_TARGET_DIR` 解耦；`mklink /J` 逻辑路径锁死。

## VS BuildTools 安装连败两次后的真凶：BackgroundDownload.exe 锁住 Installer 目录

第一次安装 `exit code 5002`（4m05s），第二次同样 5002（3m49s）。日志：

```
Error 0x80131500: Failed to extract: 文件夹 C:\Program Files (x86)\Microsoft Visual Studio\Installer
或其 中的文件已被另一个程序锁定
  at Bootstrapper.CopyContents(...)
```

**失败点在 bootstrapper 自更新**：本地 installer 是 3.14，需升到 4.12，升级动作是把整个 `Installer` 目录改名挪走再写新的。

排查路径（全部排除后才找到真凶）：

| 假设 | 验证 | 结论 |
|---|---|---|
| UAC 没弹窗 = 没提权 | `EnableLUA=0`，UAC 被系统完全禁用；写 `C:\Program Files (x86)\_test.tmp` 成功 | 排除，本来就是管理员 |
| 目录 ACL 拒绝 | 逐条打印，**全是 Allow 无 Deny**，Administrators FullControl，Owner=BUILTIN\Administrators | 排除 |
| 父目录缺 DELETE_CHILD | 父目录 ACL 同样正常；在父目录下新建子目录并 rename 成功 | 排除 |
| 沙箱拦 Program Files 的 rename | 在 `Program Files (x86)` 下新建目录并 rename → OK | 排除 |
| 是重解析点/junction | `LinkType` 为空，`Attributes: Directory` | 排除 |
| explorer 占用 | 重启 explorer 后仍被拒 | 排除 |
| 目录内某个文件被独占 | **目录内 6 个子项逐个 rename 全部成功** | 关键线索：目录本身被锁，不是文件 |

突破口：下载 Sysinternals `handle64.exe`（`live.sysinternals.com/handle64.exe`，416 KB）跑
`handle64.exe -nobanner -accepteula -a "Microsoft Visual Studio\Installer"`：

```
BackgroundDownload.exe pid: 15392  type: File  ...\Installer\resources\app\ServiceHub\Services\Microsoft.VisualStudio.Setup.Service\*.dll  (十几个)
```

**真凶：`BackgroundDownload.exe`（PID 15392，启动于 15:35:56，比我的第一次安装还早 20 秒）**。
它加载了 `Installer\resources\...` 下十几个 DLL，只要它活着，目录就无法改名。而每次重试安装又会 fork 新的，于是永远失败。

**解法**：`Stop-Process -Name BackgroundDownload -Force` → 立刻 rename 测试通过 → 第三次安装越过 4 分钟死亡点，`setup.exe` 主进程出现，Packages 缓存从 1916.8 → 1982.2 MB 持续增长。

**沉淀成经验**：
1. VS installer 报"目录被锁定"时，**别只看 `vs_*` 进程**，`BackgroundDownload.exe` 也会锁 Installer 目录。
2. 判断"目录被锁 vs 权限不足"的手法：**目录内子项能 rename 但目录本身不能 → 一定是句柄占用**；两者都不能 → 权限问题。
3. `handle64.exe` 是这类问题的终极定位工具，比猜进程名快得多。
4. `EnableLUA=0` 的机器上 `Start-Process -Verb RunAs` 不会弹窗（因为没有 UAC），容易误判"提权没发生"。

### 中间踩了两个坑，都不是编译器问题

**坑 1：代理 502。** 首次打包在 NSIS 下载处失败：`CONNECT proxy failed: proxy server responded 502/502`。
原因：每个新开的终端会话都从系统继承 `HTTP_PROXY=http://127.0.0.1:13622`，该代理已死。
→ 跑构建前必须清进程级 `*_proxy` / `*_PROXY` 八个变量。

**坑 2：NSIS 离线包放错层级（关键）。** 第一次把 zip 解压成 `%LOCALAPPDATA%\tauri\NSIS\nsis-3.13\`，
tauri 报 `Warn NSIS directory is missing some files. Recreating it.` 然后试图重下（DNS 11001 失败）。
查源码（`tauri-bundler/src/bundle/windows/nsis/mod.rs`）后确认**正确布局**：

- `nsis_toolset_path = <tauri_tools_path>/NSIS`，即 **zip 内 `nsis-3.13/` 的内容要直接铺到 `NSIS\` 根**（tauri 下载后执行 `rename("nsis-3.13","NSIS")`，不留外层）。
- 插件 DLL 必须在 **`Plugins\x86-unicode\additional\nsis_tauri_utils.dll`**（有 `additional` 这层，不是 `x86-unicode` 直接放）。
- 它校验 **13 个必需文件**（`NSIS_REQUIRED_FILES`）：`makensis.exe`、`Bin/makensis.exe`、`Stubs/lzma-x86-unicode`、`Stubs/lzma_solid-x86-unicode`、上面的 dll、`Include/MUI2.nsh`、`Include/FileFunc.nsh`、`Include/x64.nsh`、`Include/nsDialogs.nsh`、`Include/WinMessages.nsh`、`Include/Win/COM.nsh`、`Include/Win/Propkey.nsh`、`Include/Win/RestartManager.nsh`。**任意一个缺失 → 删整个目录重下。**
